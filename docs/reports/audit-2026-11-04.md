# Viewshed correctness, runtime, and usability audit — 2026-11-04

**Historical audit snapshot.** The [implemented fixes and validation](implementation-2026-11-04.md)
follow this audit. Findings and measurements below describe the original audited revision.

The largest immediate opportunities are to avoid unnecessary raster work, preserve valid
checkpoints, use in-process GDAL reliably, and remove repeated filesystem and aggregation work.
There are also correctness defects in cache reuse and several configurable numerical paths.
Fixing these should precede another expensive regional build.

This was an audit and proposed implementation order. During the audit, no calculation, configuration, delivered
data, or runtime behavior was changed. No regional runtime or end-to-end speedup was measured.

## Correctness and execution findings

P1 means an incorrect result or unexpectedly unbounded execution should be fixed before relying
on that path. P2 means a conditional correctness, reliability, or usability issue. These findings
were open at the audited revision; passing its existing tests did not cover their reproductions.

### F1 — P1: legacy distance caches reuse the wrong model and source slice

[`weights/distance/compute.py`](../../src/viewshed_toolkit/pipeline/weights/distance/compute.py),
lines 404–422, derives a partition name from `floor(start / source_chunk_size)` and checks only
column names before reuse. The actual output path is not content-addressed by model parameters.

At distance 2 km, changing exponential lambda from 8 km to 2 km returned `skipped_existing` and
the old weight **0.7788008**, instead of **0.3678794**. A separate `start=1, limit=1` request
reused the first partition containing two sources: the manifest reported one requested source
but two actual sources. Both cases were reproduced with the actual partition builder and tiny
synthetic lookup tables; only output-path selection was redirected.

Fingerprint the effective curve, cutoff, lookup content, schema, and exact selected source set;
validate output checksums and use a partition identity that cannot collide across slices. This
finding concerns the legacy distance builder, not the newer standalone distance-profile product.
Distance is a diagnostic in static composition, so this defect does not itself prove that the
integrated terrain weight is wrong.

### F2 — P1: whole-run resume can silently accept changed inputs

[`api/service.py`](../../src/viewshed_toolkit/pipeline/api/service.py), lines 148–170 and
215–229, validates configuration, stage identity, and output checksums, then returns before any
stage executes. It does not compare the current ordinary source files with the inputs used to
produce those outputs. A configuration hash of file paths is not a hash of their contents.

A probe with isolated synthetic configuration/output selection and a mocked producer wrote an
output from an input file; changing that input at the same path and calling
`process(..., resume=True)` returned `skipped=True` with the old output and no second producer
invocation. The process/resume implementation itself was exercised. Some shared-study
inputs have additional load-time guards; that does not protect ordinary configured DEM/CHM inputs.

Store and validate dependency-specific input identities in the run manifest, or invoke the
appropriate cache-aware validators before declaring the whole run reusable. Cover changed DEM,
CHM, geometry, and lookup contents in regression tests.

### F3 — P1: land partition reuse omits the canonical pair universe

[`weights/terrain/gdal.py`](../../src/viewshed_toolkit/pipeline/weights/terrain/gdal.py),
lines 268–285, includes DEM/vector/source input signatures but omits the lookup signature.
Water already includes it at lines 194–210 and 298. The runner accepts matching old partitions
at [`runner.py`](../../src/viewshed_toolkit/pipeline/weights/terrain/runner.py), lines 699–733.

Replacing a one-pair lookup with a two-pair lookup for the same source left expected land
metadata unchanged and the old partition accepted. The outer component contract detects the
lookup change, but its inner source execution can still reuse that old partition. Source
completion checks verify source IDs and statuses, not coverage of the new universe. Subsequent
[`weights/components.py`](../../src/viewshed_toolkit/pipeline/weights/components.py),
lines 173–179, fills the uncomputed new pair with zero. The probe verified metadata equality and
partition acceptance; this downstream zero-fill consequence was traced in source, not exercised
through a complete component rerun.

This specifically requires a lookup-only content change with unchanged configuration and other
inputs, such as a corrected or replaced lookup; changes to other fingerprinted inputs may already
invalidate reuse. Add lookup content identity to land partition provenance and a regression that
adds a target for an existing source. Unknown or uncomputed visibility must not become zero.

### F4 — P1: distance CLI silently discards `--limit` and `--start`

[`cli/compute.py`](../../src/viewshed_toolkit/pipeline/cli/compute.py), lines 17–24, does not
forward the options registered at lines 175–176 to the API, which supports both. A mocked CLI
dispatch with `build-distance-weights --limit 1 --start 500` called the API without either
argument. The `distance-weight` alias uses the same handler.

An intended bounded probe can therefore process the complete source selection. Forward both
arguments and test both commands. Fix F1 at the same time so correct forwarding also produces
correctly scoped cache reuse. Do not use these CLI bounds as a runtime safeguard before repair.

### F5 — P2: a conflicting run ID is rejected after work and possible cleanup

[`api/service.py`](../../src/viewshed_toolkit/pipeline/api/service.py), lines 231–236, executes
stages and, for complete production runs, cleanup. The manifest collision check comes at
270–280. A synthetic producer changed its output before `FileExistsError` rejected the changed
configuration under an existing run ID.

Validate run identity before any mutation or expensive execution, following the earlier check
already present in the component API. Keep paired production promotion and component promotion
contracts distinct. The probe did not run production cleanup; its ordering is established by source.

### F6 — P2: water LOS does not enforce the configured maximum sample range

[`weights/terrain/gdal.py`](../../src/viewshed_toolkit/pipeline/weights/terrain/gdal.py),
lines 956–978, gates sample visibility by horizon and land intersection, but not
`viewshed.max_distance_m`. A target cell admitted to the lookup can contain samples beyond that
range, so cell-level filtering is insufficient.

With maximum range 1,000 m, no land, a flat-Earth configuration, and target samples at 500 m and
1,500 m, the actual kernel reported joint LOS **1.0**, where the range-bounded result is **0.5**.
A 1 km attenuation cutoff masked the weighted error; with an explicit 5 km cutoff and a piecewise
curve equal to 1 through 2 km, the integrated weight was also **1.0 instead of 0.5**. Only target
geometry/land setup was mocked.

Apply the maximum range to every source/target sample before aggregation, preserving the full
sample denominator. Test independent LOS and attenuation cutoffs and the exact boundary. The
canonical small-craft configuration's horizon is shorter than its 30 km range, so this probe does
not establish an error in that default configuration.

### F7 — P2: multipart geometry order changes the observer design

[`prepare/area/sampling.py`](../../src/viewshed_toolkit/pipeline/prepare/area/sampling.py),
lines 178–198, selects the representative point before repairing and sorting polygon components.
Two topologically equal multipolygons with reversed component order selected first observers
at projected x=500050 m and x=500250 m. The probe requested one point from a maximum five-point
design; both configurations are supported. When the selected prefix includes all component
seeds, the aggregate sample set can remain the same despite changed ordering.

Normalize/repair and deterministically order geometry before selecting the central seed. Test
multipart reordering and adaptive prefixes. This is a scientific sampling change and needs an
algorithm-version/cache update; do not silently reuse partitions generated by the old design.

### F8 — P2: experimental xrspatial offsets can shift visibility by a row

[`weights/terrain/los.py`](../../src/viewshed_toolkit/pipeline/weights/terrain/los.py),
lines 517–531, uses default relative tolerance in `np.isclose` on absolute projected coordinates
and takes the first match. At northings around 5,400,000 m, neighboring 30 m rows can both match.
For coordinates `[5400000, 5399970, 5399940, 5399910, 5399880]`, looking up 5399910 returned
index **2 instead of 3**. The downstream offset is used at lines 1295–1298.

Use strict transform-derived integer offsets or zero relative tolerance with an appropriate
absolute grid tolerance, rejecting ambiguous matches. This affects the experimental backend;
the default GDAL path has separate stricter alignment logic.

### F9 — P2: experimental canopy dispatch bypasses observer grounding

The GDAL wrapper in [`los.py`](../../src/viewshed_toolkit/pipeline/weights/terrain/los.py),
lines 1130–1151, creates the private grounded canopy surface. The xrspatial route at 1255–1283
passes the canopy raster through curvature correction without that grounding step, despite
metadata claiming `observer_base_surface=endpoint_dtm` at line 1327.

A mocked xrspatial callable received a 10 m canopy surface at the observer with a 1.7 m height
argument, rather than the intended 0 m bare ground. This is a dispatch-input reproduction, **not
a native xrspatial numerical validation**. Implement equivalent private grounding/clearance or
reject unsupported canopy/backend combinations early. Do not present xrspatial as a drop-in
performance alternative until scientific parity is established.

### F10 — P2: invalid physical settings are accepted too early

[`config/loader.py`](../../src/viewshed_toolkit/pipeline/config/loader.py), lines 625–661,
constructs settings and checks sampling/batching policies but does not reject several invalid
physical ranges. Loader probes accepted zero raster resolution, negative maximum distance,
zero Earth radius, and a geographic `crs_projected='EPSG:4326'`.

[`prepare/datasets.py`](../../src/viewshed_toolkit/pipeline/prepare/datasets.py), lines 48–75,
treats distance and resolution numbers as coordinate units. Some later operations reject a
geographic CRS, but acquisition/preparation can be reached before an appropriate error; projected
feet also require explicit conversion. Validate finite positive sizes/ranges and projected metre
units, or implement unit conversion, before acquisition. Validate the applicable backend and
source-role settings together.

regional out-of-memory event. Measure peak RSS around aggregation and account for concurrent
finalization before increasing worker counts or the configured 768 MiB estimate cap.

## Making runs predictable and easy to operate

Add a read-only, role-aware `plan`/preflight before acquisition. The current
[`validate_region`](../../src/viewshed_toolkit/pipeline/api/regional.py), lines 24–41, mainly
checks the existence of four files in input-only mode. It cannot establish raster readability,
coverage, compatible native capabilities, or correct scientific settings. A proposed preflight
should show:

- Resolved stages, selected land/water role, output roots, and explicit cleanup/promotion effects.
- Input existence/readability, CRS, resolution, coverage metadata, and actual GDAL execution mode.
- Reusable versus stale stages with reasons, run-ID conflicts, and bounded source selection.
- Available disk/RAM and estimated preparation, source/observer, and output workload.
- An optional representative benchmark and a measured ETA range, distinguishing preparation,
  LOS, aggregation, and finalization. Estimates should state extrapolation assumptions.

Retain an explicit checkpoint/resume interface, but repair F1–F3 before describing it as reliable
input-aware reuse. Check F4 before exposing bounded trial commands. Expose a computation-only
target that does not render maps, while retaining an explicit visualization operation.

At the canonical 30 km range and 30 m grid, a bounding square is roughly four million pixels per
observer. Five to ten land observers on each of two surfaces imply a substantial workload per
source in the current algorithm, even with windowing and optimized native code. Whole-region completion
under one hour cannot be promised from unit tests or these tiny probes.

## Implementation and acceptance sequence

1. Repair cache identities, resume, CLI bounds, and pre-execution manifest checks. Add the
   reproductions as small regression tests; verify both unchanged-input reuse and invalidation.
2. Repair water range, deterministic sampling, and validation. Version scientific caches where
   outputs can change. Keep xrspatial experimental and gate unsupported canopy behavior.
3. Apply the first six performance changes above without changing raster resolution, observer
   count, target support, units, or missingness. Preserve paired/component lifecycle differences.
4. Benchmark a small representative set of existing open-water, coastal, and obstructed land
   windows, with cold/warm results separated. Reuse retained inputs; do not create another bulk
   archive. Record preparation, kernel, aggregation, wall/CPU/RSS/disk metrics and exact parity.
5. Only then evaluate aggregation changes and concurrency settings, and estimate a full region
   with uncertainty. Sampled/coarser modes are scientific approximations requiring explicit
   error assessment, not interchangeable speed optimizations. A GPU/native rewrite is not yet
   justified by current profiling evidence.
